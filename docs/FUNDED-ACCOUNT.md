# 납입식 모의 계정과 익일 시가 주문 계획 (`funded-w50-v1`)

기존 1억원 전진 모의 계정(`execution-v2`, [PORTFOLIO.md](PORTFOLIO.md))과 **별개의 계정 ID·개시 시점**이다.
기존 계정의 Bronze는 읽지도 다시 해석하지도 않는다. 실계좌·브로커 주문이 아니다.

## 계정 조건

| 항목 | 값 | 상태 |
|---|---|---|
| 초기 자금 | 50,000,000원 | 사용자 확정 |
| 월 납입액 | 1~24회 200만원, 25~48회 300만원, 49~72회 400만원… (24회마다 +100만원) | 사용자 확정 |
| 납입일 | 제안: 개시 다음 달부터 매월 첫 KRX 거래일 시가 30분 전(08:30 KST), 휴장일은 다음 거래일로 순연. `init`에서 명시(첫 거래일 또는 1~28일) | **제안값(미확정)** |
| 정책 | W(신규 학회 매수 리포트 → 다음 시가 진입, ATR42×5.75 샹들리에 종가 스탑 → 다음 시가 청산, 최대 30종목, 진입 NAV 5%) | 개시 시 동결 |
| 비용 | 주식 편도 0.3% | 개시 시 동결 |
| 미투자 잔액 | 무이자 원화 현금 | W 백테스트와 차이(아래) |

개시 후 ATR 기간·배수·최대 종목 수는 Bronze genesis의 `config`를 계속 따른다. 일일 연구 백테스트의 Optuna가
다른 값을 고르면 파이프라인은 차이를 경고 로그로 남기고, 기존 계정 설정으로 시세·신호·주문 계획을 갱신한다.
연구 재최적화만으로 계정을 재개시하지 않는다. 계정 자체의 정책 변경은 새 계정 ID/epoch가 필요하다.

납입일 규칙은 genesis의 `config.contribution_day`(`status`, `label`, `day_of_month`)에 동결된다. 웹 경계(zod)는
`proposed_unconfirmed`↔`제안값(미확정)`, `user_confirmed`↔`사용자 확정` 쌍만 허용해 미확정 값이 확정처럼 표시되지 않게 한다.

무수익·무비용 오라클(수익 예측이 아닌 납입 합계 검증): 24회 후 원금 98,000,000원, 48회 170,000,000원,
120회 530,000,000원 — `tests/test_funded_account.py::test_principal_oracle`.

## 개시

계정은 자동으로 시작하지 않는다(2026-10-20 현재 **미개시**, genesis 없음). 파이프라인 훅
(`backtest_momentum.py` → `paper_portfolio.capture` → `funded_account.capture`)은 genesis가 없으면 아무것도 쓰지 않는다.
사용자가 개시 시점과 납입일을 결정한 뒤 운영자가 기본값 없는 명령으로 append-only genesis를 쓴다.

```powershell
# epoch: 지금부터 24시간 이내의 시각(시간대 필수, 공표 W 보유 목록 생성 시각 이후).
# --contribution-day: first-trading-day 또는 1~28일. --contribution-day-status: proposed | confirmed
uv run python scripts/funded_account.py init --epoch 2026-10-21T20:30:00+09:00 `
  --contribution-day first-trading-day --contribution-day-status proposed
```

`proposed`면 모든 표시(Gold·텔레그램·웹)에 `제안값(미확정)`, `confirmed`면 `사용자 확정`이 붙는다. genesis는
다시 쓸 수 없으므로 규칙을 바꾸려면 새 계정 ID/epoch가 필요하다. 개시 후 genesis·납입·세션·계획 파일은
`refresh-daily`의 `git add data/bronze/portfolio`로 커밋된다(로컬에서 개시했다면 해당 파일을 커밋해야 CI가 같은 계정을 이어 간다).
초기 매수 후보는 개시 시점에 공표된 W 보유 종목이며(과거 수량·수익은 승계하지 않음), 이후에는 개시 후
처음 관측한 학회 매수 리포트만 신호가 된다.

## 저장 위치와 모델

| 레이어 | 경로 (`scripts/lake.py`) | 내용 |
|---|---|---|
| Bronze | `BRONZE_FUNDED/account.json` | genesis: epoch, 동결 설정, 개시 후보, 개시 시점에 이미 알려진 리포트 ID |
| Bronze | `BRONZE_FUNDED/contributions/{회차:04d}.json` | 납입 현금흐름. 파일명 = account+회차 중복 방지 키 |
| Bronze | `BRONZE_FUNDED/signals/{report_id[:24]}.json` | 개시 후 처음 관측한 매수 리포트(관측 시각 포함) |
| Bronze | `BRONZE_FUNDED/sessions/{KR\|US}/{date}.json` (+`~NN` 추가분) | 완료된 세션의 시가·종가·ATR·관측 환율 |
| Bronze | `BRONZE_FUNDED/plans/{KR\|US}/{date}/{정책버전}/rNN.json` | 동결된 주문 계획. account+시장+거래일+정책버전 디렉터리, 개정은 rNN |
| Silver | `SILVER_FUNDED_LEDGER` | Bronze 재생 원장 |
| Gold | `FUNDED_ACCOUNT` = `public/research/funded-account.json` | 웹 경계 `src/lib/funded-account.ts`(zod), 로더 `src/lib/funded-account-data.ts` |

- **계획(plan)**: 시장별 마지막 완료 종가로 만든 다음 실제 거래일 시가 주문. KRW 예산과 종가 기준 **추정** 수량,
  현재→계획 비중, 사유, 조건, 납입·선행 계획 예약을 담는다. 대상 시가를 보지 않는다.
- **체결(fill)**: 다음 세션 기록에 실제 시가가 생긴 뒤에만 재생 원장이 만든다. `plan_id`·`order_id`로 계획을 가리키며
  계획과 같은 객체가 아니다. 계획의 추정 수량을 체결 수량으로 표시하지 않는다.
- **개정/취소**: 같은 시장·거래일 계획을 다시 만들 때 결정이 같으면 새 파일을 쓰지 않는다. 시가 전 새 관측(예: 늦게 수집된
  리포트)이 결정을 바꾸면 `r02`가 `supersedes`와 `revision_reason`을 가진다. `funded_account.py cancel --market KR --day …
  --reason …`은 주문 없는 `cancelled` 개정을 쓴다. 취소는 최종이다: 이후 파이프라인 재실행은 계획을 다시 활성화하지 않고,
  `funded_account.py uncancel --market … --day … --reason …`(시가 전, 현재 데이터로 재작성)만 되살린다. 결정 비교는
  방향·종목·추정 수량·제외·납입만 보며 부동소수 예산의 몇 원 차이로는 개정·재전송하지 않는다. 대상 시가가 지난 계획은 바꿀 수 없다.

## 시점

- KR 계획은 KR 15:45 KST 이후 완료 종가, US 계획은 16:15 New York 이후 완료 종가로만 만든다(`market_clock.closed_bar_end`).
  18:30 KST 실행에서 US 계획의 기준일은 직전 뉴욕 세션이며 그날 밤 열릴 세션의 종가는 존재할 수 없다.
- 다음 실제 거래일은 `scripts/market_calendars.py`의 KRX/NYSE 휴장표로 시장별로 정한다(2026–2027 수록).
  2026-10-20 검증: NYSE 공식 페이지 = exchange_calendars 4.13.2 XNYS와 일치. KRX는 XKRX와 일치하되 라이브러리에 없는
  2026-06-03(지방선거)·2026-07-17(제헌절, 2026년 공휴일 복원)을 거래소 발표대로 휴장 처리했다. 2027-05-03·07-19
  대체공휴일(토요일 노동절·제헌절)은 정부안 단계라 넣지 않았다. 12월 KRX 2027 휴장 공고 뒤 갱신한다.
- 특수 장시간: NYSE 13:00 조기 폐장일은 기존 16:15 NY 컷오프가 더 늦어 그대로 안전하다. KRX 수능일(2026-11-19,
  2024·2025년처럼 10:00–16:30 가정)은 실제 종가+15분(16:45 KST)까지 그 세션을 완료로 보지 않는다. 첫 거래일 10:00 개장은
  계획 동결 기준 09:00보다 늦어 규칙 변경이 없다.
  표 범위 밖이면 실패하고, 벤치마크(KOSPI/S&P500)에 휴장일 시세가 있으면 표 오류로 실패한다.
- 시장 데이터 준비 = 해당 시장 벤치마크의 기대 세션 시세 존재. 없으면 세션·계획을 만들지 않는다.
- 계정 평가액은 시장별 최근 종가(KR·US 기준일이 다를 수 있음)로 계산한다. Gold `marks`와 계획의 `account_snapshot.marks`에 표시한다.

## 결정 규칙

| 상황 | 계획(종가 시점) | 체결(실제 시가) |
|---|---|---|
| 신규 매수 신호 | 리포트일 < 주문일, 관측 시각 ≤ 동결 시각인 신호만. 예산 = 추정 NAV × 5% | 예산 한도 안에서 시가로 정수 수량 재계산(내림) |
| 갭 상승 | 수량은 추정치로 표시 | 수량 축소. 시가 기준 1주 미만이면 미체결, 신호 소멸 |
| 현금 부족 | 가용 현금 < 예산 50%면 제외(신호 소멸, W와 동일) | 실행 시 현금 < 예산 50%면 미체결·소멸, 아니면 남은 현금까지 |
| 정수 주식 | 1주 가격 > 예산이면 제외 | 소수 주식 없음 |
| 거래정지·누락 시가 | 기준일 종가 없으면 보류(재평가) | 시가 0·없음·거래량 0이면 미체결. 매수는 최대 5회 계획까지 재시도 후 만료, 스탑 매도는 다음 거래일 계획에 다시 포함 |
| 스탑 매도 | 종가 < 샹들리에 스탑이면 다음 시가 전량 매도. 수량 확정, 금액 추정 | 시가 매도 |
| 동시 주문 자금 순서 | 먼저 열리는 시장의 미체결 계획 예산을 예약하고 그 뒤 계획을 만든다. 같은 시장은 매도 → 납입 → 매수(리포트일, 학회 수, 티커 순) | 체결도 시각 순. 같은 시장 매도 대금은 같은 시가 매수에 사용 |
| 신규 납입 | 시가 전 도착분을 가용 현금·추정 NAV에 포함. 기존 보유 종목 비중 맞추기 매수는 하지 않음(W는 강제 리밸런싱 전략이 아님) | 08:30 KST 입금. 늦게 기록되면 기록 시각부터 유효(`late`) |
| 슬롯 | 최대 30종목(두 시장 합산, 같은 시장 매도분 반영) | 체결 시 30종목이면 미체결·소멸 |
| 주문 불가 상품 | `INDEX:*`·합성 상품·형식이 아닌 코드는 `not_orderable`로 제외 | — |

`INDEX:AllWeather`(올웨더 합성지수)는 거래 가능한 상품·시가가 없어 주문하지 않는다. W 백테스트는 미투자 잔액을 이
합성지수에 파킹하지만 이 계정은 무이자 원화 현금으로 둔다. 따라서 성과는 W 백테스트와 같지 않다.
거래 상품 매핑은 KR 6자리 코드 → `KRX:{code}`(KRW, 1주 단위), US 티커 → `US:{ticker}`(USD, 1주 단위, 원화에서
직전 관측 환율로 추정·환산)이다. 매일 목표 비중으로 강제 리밸런싱하는 정책은 구현하지 않았다. 추가한다면 별도 정책
버전으로 만들고 비용·회전율을 비교한다.

## 성과 계산

재생은 Bronze에 마지막으로 기록된 시각(`as_of`)까지만 적용한다. 계획 시점에 기록된 내일 08:30 납입은
`scheduled_contributions`로만 보이고 원금·현금·평가액·XIRR에는 입금 시각이 지난 뒤 들어간다.

- 누적 원금 = 초기 자금 + 적용된 납입 합계. 투자 손익 = 평가액 − 누적 원금.
- TWR(납입 제외): 세션 종가 평가마다 `평가액 / (직전 평가액 + 그 사이 납입)`을 연쇄 곱한다. 납입은 수익률에 들어가지 않는다.
- XIRR: 30일 이상 경과했을 때만 계산(그 전에는 `null`). 참고 지표다.

## 텔레그램

`scripts/send_telegram_orders.py`가 기존 `send_telegram_portfolio.py`의 분할(`chunk`)·발송·영수증·실패 처리(`deliver`)를
재사용한다. 메시지: 시장·기준일·다음 실제 거래일·자산·방향·수량(추정/확정)·예산 또는 금액·현재→계획 비중·사유·추정 비용·
현금·납입·체결 조건·제외 사유·납입 규칙 `제안값(미확정)`.

- 시장별로 **오늘의 계획**만 보낸다: 그 시장의 최신 완료 세션 기준이고 대상 시가가 시작 전이어야 한다.
  아니면 그 시장은 보내지 않고 종료 코드 1로 실패해 지연을 드러낸다. 오래된 계획을 오늘 계획으로 재전송하지 않는다.
- 영수증 키는 `sha256("orders:{plan_id}:{chat}")`: 같은 개정은 한 번만, 개정(r02)은 새로 보낸다.
- `.github/workflows/funded-orders.yml`은 고정 시각이 아니라 main의 `refresh-daily` 또는 수동 `full-sweep-manual` 성공
  (둘 다 같은 백테스트 훅으로 계획을 동결하고 `funded_account.py --check` 게이트를 통과) 뒤 `workflow_run`으로 실행한다.
  영수증 캐시는 restore/save로 나눠 실패한 실행에서도 저장한다(부분 전송 후 재실행 시 성공한 계획은 다시 보내지 않음.
  한 계획의 메시지 일부만 간 경우는 그 계획 전체를 다시 보낸다). 수동 실행 기본값은 dry-run이다.

```powershell
uv run python scripts/send_telegram_orders.py --dry-run
uv run python scripts/send_telegram_orders.py --dry-run --data <다른 산출물> --now 2026-10-19T11:35:00+00:00
uv run python scripts/funded_account.py --check
```

Secrets `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` 설정 방법은 [PORTFOLIO.md](PORTFOLIO.md#알림-설정)와 같다.

## 백테스트 구간과 실전 구간

| 구간 | 기간 | 만든 것 | 성격 |
|---|---|---|---|
| 백테스트 구간 (simulated) | 2023-07-03 ~ 실전 개시 직전 | `scripts/funded_backtest.py` → Silver `data/silver/portfolio/funded-w50-v1-backtest.json` | 모의. 동결된 실전 계획이 아님 |
| 실전 구간 | 개시(epoch) 이후 | `funded_account.py` Bronze 계획·세션·납입 → Silver/Gold | 시가 전에 동결된 실전 계획 |

- **같은 결정 코드.** 백테스트는 메모리 안에서 매일 20:30 KST 파이프라인 저녁을 흉내 내며 실전과 똑같이
  `build_plan`(기준 종가로 동결, 대상 시가를 보지 않음)과 `_run`(실제 다음 시가 체결, 정수 주식, 납입은 원금)을 호출한다.
  세션은 시장별 컷오프 뒤에만, 신호는 공개 시각 뒤에만 들어온다. 미래 시세를 바꿔도 그 이전 체결은 바뀌지 않는다
  (`tests/test_funded_account_seed.py`).
- **신호 공개 시각(availability).** 아카이브는 2026-06에 일괄 수집되어 파이프라인 최초 수집일(first_seen)을 쓰면
  2023-07~2026-06에 신호가 없고 2026-06-09 하루에 600여 건이 몰린다. 그래서 공개 시각 기준은 산출물의
  `availability`에 명시한다: `publication_date`(발간일 저녁 공개, W 백테스트와 같은 가정 — 이 파이프라인의 관측이 아님) 또는
  `first_seen`. 화면·알림은 이 가정을 구간 설명에 표시한다.
- **납입.** 시작일 2023-07-03(7/1은 토요일)에 초기 5천만원과 1회차가 08:30 KST에 들어간다. 매월 첫 KRX 거래일(사용자 확정),
  1~24회 200만원, 25~48회 300만원(2025-07부터), 49회부터 400만원…. 실전은 백테스트의 회차 번호를 이어 간다.
- **seed.** 실전 genesis(`init --seed-backtest`)는 백테스트 종료 상태(현금·보유 종목·원금·적용 회차·대기 신호·이미 본 리포트)를
  명시적으로 담고, 백테스트 산출물의 내용 해시(`artifact_sha256`)와 `run_id`, 기간을 기록한다. Gold 재생은 해시가 다르면 실패한다.
  백테스트 마지막 시가 계획 중 체결 기록이 없는 것은 승계하지 않고, 그 신호는 대기 신호로 넘어간다.
- **이음매 규칙(seam).** 백테스트는 입력 스냅샷에 있고 마지막 모의 결정 시각(`end_at`)까지 공개된 리포트만 "소유"한다.
  그 리포트는 백테스트 안에서 체결·탈락하거나, 체결 전이면 대기 신호로 실전 genesis에 넘어간다(관측 시각은 백테스트의
  공개 시각 그대로). 실전 genesis의 이미 본 리포트 = 백테스트 시작 전 공개분 + 백테스트 신호 전부이므로 실전은 이들을
  다시 신호로 만들지 않는다(이중 진입 없음). 그 밖의 모든 리포트 — `end_at` 이후 공개분, 또는 그 전에 공개됐지만
  백테스트 실행 뒤에 처음 수집된 리포트 — 는 실전 파이프라인이 처음 관측한 시각에 실전 신호가 된다(누락 없음).
  `tests/test_funded_account_seed.py::test_seam_reports_are_neither_dropped_nor_entered_twice`.
- **성과 분리.** Gold `segments.backtest`·`segments.live`·`segments.combined`. 실전 손익 = 평가액 − 개시 평가액 − 실전 납입,
  실전 TWR은 개시부터. 합산 TWR = (1+백테스트)×(1+실전)−1. `performance`는 계정 잔고 합계이며 `scope:
  combined_backtest_and_live`로 백테스트 포함임을 표시한다. 웹 경계(zod)는 실전 손익에 백테스트 손익을 섞거나
  라벨 없이 합산하면 거부한다. `history` 행은 `segment`를 가진다.
- **검증 경계.** `funded_backtest.py --check`는 로컬 시세(git 제외)로 전체를 재계산해 비교한다. CI의
  `funded_account.py --check`는 Bronze 재생과 백테스트 산출물 해시 일치를 검사하며 시세 재계산은 주장하지 않는다.
