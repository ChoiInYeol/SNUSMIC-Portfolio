## 1. 사용자 결정·제약 (반드시 지킬 것)

- **파싱 엔진은 kordoc 고정** (https://github.com/chrisryugj/kordoc, `tools/kordoc` 에 4.22.13 고정). 다른 엔진 제안 금지.
- **CPU 사용 제한**: 사용자가 렉을 호소했다. 무거운 작업은 동시 작업 4개 이하, 낮은 우선순위, 8코어 affinity 로 돌린다.
  affinity/우선순위는 **부모 셸에 먼저 걸어야** 자식(node 워커)이 상속한다:
  ```powershell
  $me = Get-Process -Id $PID; $me.ProcessorAffinity = [IntPtr]0xFF; $me.PriorityClass = 'BelowNormal'
  & .venv\Scripts\python.exe scripts/transcribe_pdfs.py --jobs 4
  ```
- `main` 푸시 = Vercel 프로덕션 배포. 사용자 확인 없이 `main` 에 푸시하지 말 것. 브랜치 푸시는 프리뷰만 만든다.

## 2. kordoc 성능 함정 (가장 중요한 발견)

kordoc 은 OCR 모델이 `~/.cache/kordoc/models/ppocr` 에 캐시돼 있으면 **`--ocr` 없이도 PDF 안 이미지(차트)를 자동 OCR** 한다.
같은 39쪽 PDF가 1.7초 → 70초(CPU 900초)로 느려지고, 추가되는 글자는 대부분 저신뢰 차트 텍스트다. 공식 끄기 옵션은 없다.

해결(이미 반영): `scripts/transcribe_pdfs.py` 는 텍스트층 단계에서 `KORDOC_MODEL_CACHE=cache/kordoc-no-models`(빈 폴더)를 준다.
kordoc 품질 판정(`pageQuality.needsOcr`)상 표지(1~3쪽)나 문서 과반이 텍스트층이 없을 때만 `--ocr` 단계(실제 모델 캐시)를 돌린다.
→ 이 수정 전 측정한 "문서당 12.7초 / 전체 하루 이상" 추정치는 **틀렸다**. 텍스트층 문서는 장당 0.05~0.1초 수준.

추가로 OCR의 ONNX 세션은 기본 스레드 풀이 CPU affinity보다 커질 수 있다. 프로젝트 소유
`tools/kordoc/cpu-limits.mjs`를 Node `--import`로 로드해 세션당 intra-op 2 / inter-op 1로 제한한다.
이미지 전처리 libvips도 1스레드로 제한한다. Windows에서는 절대 경로 대신 `Path.as_uri()`를 전달해야 한다.
kordoc 패키지·모델·해상도는 바꾸지 않는다.
읽을 수 있는 본문은 유지하면서 불량 표지 페이지만 병합하고, 대부분 스캔인 문서는 모든 불량 페이지를 OCR한다.
완료 문서는 배치 끝을 기다리지 않고 즉시 원자적으로 저장하며, 일부 실패도 nonzero 종료로 게시를 막는다.
텍스트층 속도를 전체 작업 시간으로 외삽하지 말 것. YIG·KUVIC의 이미지 문서는 본문 수십 쪽 전체에
실제 OCR이 필요하다. 진행 여부는 프로세스 존재만 보지 말고 개별 저장 로그·현재 헤더 수·CPU 증가로 확인한다.

## 5. 평가 결과 (company 224건)

`error` = (wrong+missed+spurious)/n, `critical` = (wrong+spurious)/n — 틀린 값은 빈 값보다 해롭다.

| 방식 | rating | target | current | upside | ticker | 전체 err / crit |
|---|---|---|---|---|---|---|
| A 기존 정규식 + 구 전사 | 4.5 / 2.7 | 17.4 / 8.0 | 29.9 / 7.1 | 35.3 / 1.8 | 9.8 / 0.9 | **19.4 / 4.1** |
| A' 새 추출기 + 구 전사 | 8.0 / 0.0 | 9.4 / 3.6 | 33.0 / 3.1 | 15.2 / 3.1 | 9.8 / 0.9 | **15.1 / 2.1** |
| B 기존 정규식 + kordoc 표지 | 3.1 / 1.8 | 12.9 / 5.4 | 21.4 / 3.6 | 35.7 / 1.3 | 13.4 / 0.4 | **17.3 / 2.5** |
| C 새 추출기 + kordoc 표지 | 8.9 / 0.0 | 11.2 / 4.5 | 18.8 / 1.8 | 13.8 / 4.0 | 13.4 / 0.4 | **13.2 / 2.1** |
| D C + 발간일 종가 정합 | 8.9 / 0.0 | 11.2 / 4.0 | 18.8 / 1.8 | 13.8 / 4.0 | 13.4 / 0.4 | **13.2 / 2.1** |

고신뢰 라벨만(198건): A 18.9/3.4 → C·D 12.9/1.5. 재현: §3-2 명령 (`cache/eval.json` 에 실패 목록 포함).

**결론**: kordoc + 새 추출기(C)가 전체 오류를 19.4% → 13.2%, 틀린 값을 4.1% → 2.1%로 거의 절반으로 줄인다.
엔진 효과(A→B 19.4→17.3)와 추출기 효과(B→C 17.3→13.2)가 모두 있다. D(종가 정합)는 목표가 치명오류만 소폭 개선 — 시세 의존을 늘릴 가치는 낮다.

**다음 개선 후보 (eval.json 실패 목록으로 확인할 것)**
- rating: C는 틀린 값 0건이지만 누락 8.9%. B(기존 정규식)는 누락이 적다 → **C가 None일 때만 기존 parse_rating 값을 쓰는 하이브리드**가 유력.
- ticker 9.8%(구 전사 전체본) → 13.4%(kordoc 표지): 표지만 읽어서인지, kordoc 레이아웃에서 identity 파서가 놓치는지 분리 확인.
- ewha: 새 추출기의 치명오류가 구 전사본 1건 → kordoc 표지 8건. ewha 표지 레이아웃을 kordoc이 어떻게 내는지 확인.
- current 누락 18.8%: 표지에 현재가가 "주가(날짜)" 행으로만 있는 경우(voera·ewha 라벨러 메모) — `CURRENT_LABEL` 의 `주가\s*\(` 패턴 커버리지 점검.
